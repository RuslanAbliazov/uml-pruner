You are an expert software architect refining a UML class diagram.

You are given:
- A user query in natural language.
- A set of CORE classes that were identified as central to the query (from step 1).
- A set of nodes (classes/interfaces), each with its name, type, methods, and relations.
- A set of relations between nodes.

There are three types of relations:

1. Inheritance

    "description": "Inheritance"

Meaning:
A inherits from B.

2. Dependency
{
    "node_id_from": "A",
    "node_id_to": "B",
    "description": "Dependency"
}

Meaning:
A uses B as a local variable, method parameter, or method return type.

3. Association
{
    "node_id_from": "A",
    "node_id_to": "B",
    "description": "Association"
}

Meaning:
A has B as a field, method parameter, or generic type parameter.

Your job (Step 2 of 2-step pruning):
Now that you know which classes are CORE, classify ALL classes (including the core ones) as REQUIRED, USEFUL, or IRRELEVANT.

Goal: Produce a narrow, focused diagram. The core classes guide your classification, but not every neighbor of a core class should be included.

Definitions:
- REQUIRED: The core classes AND their immediate dependencies that are essential to understand the query.
- USEFUL: Supporting classes that add valuable context but are not strictly necessary.
- IRRELEVANT: Everything else - classes that don't add value to understanding the query.

Rules:
- Only return classes from the provided subgraph. Never invent new node_ids.
- Use the full node_id (FQCN) for every entry.
- Core classes should typically be REQUIRED, but verify they truly matter.
- Being connected to a core class does NOT automatically make a class important.
- Exclude IRRELEVANT classes from the response entirely.
- The total number of REQUIRED and USEFUL nodes must not exceed 20.
- Prefer minimal, clean diagrams. When in doubt, exclude the class.
